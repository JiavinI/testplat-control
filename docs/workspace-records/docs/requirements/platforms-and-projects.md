## 被测对象与关系

GO2、E3E3 本身都是独立的被测网站平台，包含搜索商品、下单、选择物流、支付、售后等订单操作。公司还有 E3HUI 等网站项目；本次明确新增的账号范围是 GO2、E3E3，不凭空补充其它网站的地址或登录配置。

GO2 有自己的 GSB，E3E3 也有自己的 GSB。用户从所属网站登录后进入该网站的 GSB，GSB 沿用所属网站的登录身份。

```text
GO2 网站平台
└── GO2 的 GSB（沿用 GO2 登录身份）

E3E3 网站平台
└── E3E3 的 GSB（沿用 E3E3 登录身份）

代发管理后台 daifa_admin（独立入口、独立登录）
代发拿货端 daifa_picker（独立入口、独立登录）
GO2 管理后台 admin_go2（独立入口、独立登录）
```

这张图表示业务归属和登录关系，不断言物理部署是否独立。即使多个 GSB 使用同一个 API Host，也不能将其网站归属、账号和登录上下文合并。

代发后台等管理平台可以选择业务项目，管理对应网站的订单，包括任务分派、发货、售后退款、商品出入库等。拿货端处理管理后台下发的拿货任务。后台选择“GO2 的订单”和选择“GO2 网站作为被测平台”是不同含义；GO2 网站与 GO2 管理后台也是两个不同平台。

## 对 TestPlat 的要求

- 被测平台应作为选择入口，并保留管理后台选择业务项目的能力。
- 必须能分别管理和测试 GO2 网站、GO2 的 GSB、E3E3 网站、E3E3 的 GSB，以及上述独立后台。
- 网站与自身 GSB 的归属关系、后台处理订单的项目归属需要分别表达，不能用一个通用项目下拉框混为一谈。
- GSB 通用接口定义可以考虑复用；所选网站、适用 Host、登录来源、账号和登录缓存必须正确隔离。
- GSB 沿用网站登录身份，不代表浏览器 Cookie 与 API token 必须相同；按真实协议与旧配置核对。
- 独立后台使用自己的账号和鉴权；切换订单所属项目不自动套用网站账号。

用户已确认：四个功能菜单内采用平台＋项目两级选择。平台提供 GO2 网站、E3E3 网站、GSB、代发后台、拿货端、GO2 管理后台；GSB 项目选 GO2 或 E3E3，标题明确显示「GO2 的 GSB／E3E3 的 GSB」。网站本身可独立选择测试。后台切换业务项目不自动更换后台身份，不凭空向业务接口注入项目字段。

## 现状与实施边界

当前代码和数据库只建有 `main/gsb`，有一个 test 环境和已验证的 `gsb.b2.primary`。当前登录模板 `source` 固定为 `go2`；这只是已有实现，不能用来反推用户业务关系。增加 E3E3 必须处理登录来源及缓存隔离。

当前 Web 运行默认使用数据库环境和账号，Git 保存接口定义与登录流程；此边界继续有效。现有预览库、账号、主密钥、历史记录及未提交工作必须保留，不删除重建，不直接重命名已有记录来假装迁移。数据变更方案先在隔离库或隔离副本验证。

代发后台旧登录依赖 Redis 验证码，当前 Web 执行链路存在连接配置适配缺口；保存配置与真实登录成功需分别报告。CAT 是旧配置盘点发现项，不因发现配置就自动加入本次范围。

本轮不扩展 Page 执行、复杂场景编排、测试数据、套件或通用 Assets 编辑器，不进行真实下单、支付、退款、出入库操作；不远程推送、合并或发布。
