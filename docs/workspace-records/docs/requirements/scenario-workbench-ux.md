# 场景工作台体验重设计

状态：设计建议与交互原型。用户当前倾向 B「目录检查器」；整页正式 UI 尚未定稿，不构成共享参数或个人草稿的产品决定。
日期：2026-10-20

## 使用主线

测试人员进入场景后，先确认场景目标、环境和步骤顺序，再确认身份/接口信息，必要时调整本次参数，运行后沿用同一编号定位结果。主页面以有序步骤为主体；文件大小、路径、修改时间等归入资产详情，不抢占首屏。固定解释文案改为字段旁提示、来源标签和按需展开。

步骤展示稳定的结构序号（如 `1`、`1.1`、`1.2`、`2`），不是后端 `step_id` 的替代品。日志节点继续保存现有 `step_id` 与父子 trace；前端用同一遍历规则显示序号、标题和父步骤，失败摘要可跳回对应编号。重排步骤后序号自然变化，历史结果应依据当次 trace 顺序生成，不从最新定义推导历史顺序。

步骤标题优先级：显式 step name、目标资产 display name、step_id。API 子项突出 method + URL；身份使用显式 identity。未指定时显示“未显式指定，按接口配置”，运行历史以实际 auth 记录为准。flow 可能包含多个身份，不能汇总成臆造的单一角色。缺少资产详情时保留 asset_id，不凭文件名猜业务操作。

## 参数编辑与复用

参数默认在抽屉/检查器编辑，字段模式固定展示 key/path，仅编辑 typed value；高级 JSON 入口与字段编辑互相同步。嵌套编辑必须保留同一顶层键的兄弟字段，符合当前顶层键替换规则。运行按钮旁展示当前值来源摘要，完整优先级、revision 和生效值放在按需查看区域。

常规编辑只改变 value，不要求测试人员重新输入键。字段应支持业务名称/描述（缺少时保留真实路径，不臆造），按业务分组或“被哪些步骤引用”筛选；数字、布尔、字符串分别编辑，数组/对象有专门编辑或高级 JSON。空字符串、0、false、null 与“未提供”分开处理。高级 JSON 是同一工作副本的另一编辑视图，离开前对未应用内容明确选择应用或放弃。

原有“维护默认值”改到数据抽屉内的“团队默认设置”，明确全部适用环境与使用范围；“维护 test 覆盖”改为“test 环境差异”，只展示相对团队默认的差异。一般使用者主要选择数据方案、编辑当前草稿；维护者才需要进入默认设置。刷新参数成为来源详情中的重新加载动作；当前有编辑时先比较新旧差异，不静默清空。生效预览默认只有字段、值、来源三项，详细覆盖链放在来源详情。

`common`、`private` 是场景作者在参数路径中使用的普通键名。界面应显示完整路径并将它们作为可编辑分组名；不能暗示前者全局共享、后者对用户私有。当前值来源依次由既有参数上下文决定；环境级覆盖可能影响其他使用同一配置的用户。明确标记“团队共享”及影响范围。

建议未来提供两层复用：

- **我的草稿**：按平台用户、项目、场景、环境保存未发布工作副本。自动保存输入值；资产提交或 schema 变化时校验并提示冲突。该能力需要身份隔离存储和版本检查，现有系统尚未提供。
- **团队数据方案**：用户显式命名保存/更新的可共享输入集合，显示作者、更新时间、环境和场景 revision。使用者先复制为个人草稿再编辑；只有明确的共享保存动作写回，使用 CAS/revision 防止覆盖他人新版本。现有 asset_default、environment_override 是共享配置保存能力，但不是具名方案。

从历史复制输入应生成草稿而非改变共享默认，并排除 token、cookie、秘密值、运行期输出和动态业务 ID；复制后逐项检查。一次运行冻结完整参数快照、来源和配置 revision，不能把后来值伪装成当时值。运行输入只修改共享环境覆盖的规则遵循 ADR-003，原型里的“团队方案”目前仅为交互占位。

方案不是新增的一层隐式优先级：选择后初始化工作副本，明确列出相对当前资产/环境基线的差异；环境或资产版本变化时提示重新校验，不自动带入另一个环境。草稿自动保存要显示保存中/已保存/保存失败，失败时保留当前输入；团队更新采用显式确认及 revision 比较。环境差异继续遵循原有覆盖顺序。业务输入中的动态 ID 需要检查有效性后选择保留/重填，不能从响应输出无差别复制回运行参数。

## 页面方案

- **A 步骤主屏**：紧凑运行栏 + 全宽步骤序列 + 参数抽屉。适合反复运行和看顺序，默认视线聚焦在操作链。
- **B 目录检查器（当前倾向）**：左侧编号目录，右侧直接展示选中步骤详情。适合复杂场景快速跳转、检查局部绑定；目录明确选中态，详情按请求/身份、输入映射和按需展开的原始数据组织。
- **C 执行时间线**：环境/方案作为运行上下文节点，步骤呈纵向执行轨迹。适合运行中与历史结果并排理解。

原型样式可参考紧凑请求信息栏、清晰编辑边界和分段层级，但保留场景调用语义，不照搬接口编辑器。当前 B 为 DEV 原型迭代方向；整页 UI 后续专门重设计。

三个方案使用同一真实场景定义和资产元数据。当前示例只有匿名 loopback echo API；身份显示“未指定身份”，只展示真实 method/path。原型不发请求、不写参数服务、不记个人草稿；运行结果为内存模拟。

## 现有能力与落地边界

现有场景参数定义、步骤引用、嵌套 trace、资产默认和环境覆盖、revision/CAS 保存、运行历史均已存在。当前单次 JSON 覆盖只驻留组件状态，刷新/重新进入丢失。没有按用户隔离草稿或具名共享方案模型。参数来源按顶层键替换，不做深合并；身份与 API method/path 的数据应来自已有运行 auth 和资产 metadata/describe，不由界面猜测。

后续落地建议先按所选布局改场景主屏与编号结果导航；再实现字段型参数编辑和单次输入恢复；另行设计个人草稿存储及团队方案 API/权限/revision，再开放跨用户共享。后两项涉及持久化及数据归属，应先补充具体设计/决策与迁移验收，不由本原型直接实现。

## 验收方向

首次进入能在无需展开参数面板时读懂全部顶层步骤顺序；嵌套层级序号在运行与历史详情一致；step 标题/API/身份没有虚构；key 始终可见且修改嵌套值不丢兄弟字段；参数方案的个人/共享范围和保存动作明确；移动端无横向溢出；非开发构建不显示原型切换器。
