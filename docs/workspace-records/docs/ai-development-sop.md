# TestPlat AI 开发 SOP

## 这份 SOP 解决什么问题

SOP（Standard Operating Procedure，标准作业流程）是一份可重复执行的操作说明。它回答的是“这类工作每次按什么顺序做、每一步交付什么证据、什么条件下才能进入下一步”。

本项目同时使用两类文档：

- `docs/ai-development-workflow.md` 解释长期工作方法、会话切换和交接原则。
- 本 SOP 规定一次具体需求从提出到交付的操作步骤和放行门槛。

它们不是重复关系。工作流是规则，SOP 是按规则执行的一张检查单。需求、架构决策、任务状态和交接记录仍分别以 `CONTEXT.md`、`docs/decisions/`、`tasks/current.md` 和 `notes/handoff-*.md` 为准。

## 什么时候使用

以下工作都使用本 SOP：

- 新增或修改 Control、Engine、Assets 的功能。
- 修改接口、账号、环境、登录、场景或执行链路。
- 修复跨仓库问题，或需要确认旧接口是否仍兼容。
- 一轮代码审查后的修复和复审。
- 需要让新 AI 会话接手已有工作的阶段切换。

以下情况只需要直接操作，不必完整走一遍：

- 只改错别字、注释或不会影响行为的排版。
- 只查询日志、查看状态或运行已有命令。

如果一个看似很小的修改会影响接口契约、数据结构、认证、执行结果或兼容行为，应升级为完整 SOP。

## 参与者和职责

### 用户

用户负责确认业务目标、优先级、验收标准和外部动作授权。用户不需要指定实现细节，但需要判断“这个行为是否符合测试人员使用方式”。

### AI

AI 负责定位代码、提出最小方案、实现、测试、审查和记录证据。AI 不把“代码能运行”直接当成“需求完成”，必须区分测试通过、假服务通过和真实被测系统通过。

### 仓库和文档

代码、测试、配置和决策文件是事实来源。聊天内容可以帮助理解意图，但不能替代任务状态或验收证据。

## 标准流程

### 1. 受理需求

先把用户描述整理成一条可验证的目标：

```markdown
目标：用户完成什么操作后，系统出现什么结果？
本轮不做：哪些相邻能力明确延后？
涉及：Control / Engine / Assets 哪些仓库？
验收：用什么操作、测试或真实业务结果证明完成？
风险：依赖、兼容、数据、凭据或远程发布风险是什么？
```

完成标准：目标可以写成一个最小切片，且有至少一条用户可观察的验收条件。若目标仍包含多个独立闭环，先拆分，不进入实现。

### 2. 读取上下文和检查工作区

按顺序读取：

1. `AGENTS.md`、`CONTEXT.md`。
2. `tasks/current.md`。
3. 本 SOP 和 `docs/ai-development-workflow.md`。
4. 涉及的 `docs/decisions/*.md`。
5. 跨会话时读取最新 `notes/handoff-*.md`。

随后检查三个子仓库的工作区、分支、最近提交和相关 diff。先确认已有未提交修改和正在使用的预览数据，再决定修改范围。

完成标准：能够说清当前切片的入口、数据流、现有测试、未完成项和不可触碰的数据；没有把旧聊天中的猜测当成事实。

### 3. 复述并确认方案

AI 用自己的话复述目标、非目标、验收和风险。需要设计选择时，给出最小方案和备选方案；影响后续兼容、数据模型或用户体验的选择写入 ADR。

本阶段只解决理解问题，不提前写大量代码。用户确认方向后再实现；如果代码与需求冲突，先指出冲突。

完成标准：用户可以在几句话内判断 AI 是否理解了“做什么”和“暂时不做什么”。

### 4. 建立最小验证路径

先选一条最短的真实闭环，再扩展范围。对 TestPlat，优先顺序通常是：

1. 一个真实 API 的定义、环境、账号、登录和请求。
2. 同一个 API 的参数覆盖、响应断言和历史记录。
3. 两步场景的顺序、数据传递和失败定位。
4. 批量、数据驱动、Page 或高级编排。

完成标准：修改前已经知道将运行哪些测试、如何构造隔离数据、真实业务成功的判据是什么。

### 5. 实现一个切片

只修改当前切片需要的文件和仓库。优先复用现有领域模型、执行入口和测试夹具；不要为了“顺便整理”扩大范围。跨仓库改动必须说明契约如何连接。

完成标准：目标行为已实现，相关测试和文档同步更新，临时调试代码和秘密没有进入仓库。

### 6. 验证和审查

按改动范围执行检查，并把结果分层记录：

- 单元 / 集成测试。
- 前端 lint、build 和页面行为。
- 假服务或本地 Engine 验证。
- 真实被测系统的业务断言、账号和环境。
- 依赖来源：远程锁定版本、editable 源码或本地 wheel。

审查至少回答四个问题：

1. 需求中的每条验收条件是否有证据？
2. 旧接口、旧路径和兼容回退是否仍被调用？
3. 并发、缓存、版本、失败重试和秘密脱敏是否正确？
4. 文档、OpenAPI、测试和实际行为是否一致？

完成标准：没有把 HTTP 200 当成业务成功；失败、限制和未验证范围都已明确写出。

### 7. 收尾和交接

更新 `tasks/current.md`，记录完成、剩余、验证证据和下一步。切片完成或要切换领域时，创建 `notes/handoff-YYYY-MM-DD.md`，写明三个仓库状态、已确认决定、风险、命令和下一切片。

远程推送、合并、发布、部署或修改真实外部系统必须单独得到用户授权，并且只能在本地实现和验证完成后作为最后一步提出。

完成标准：新会话只读取入口文档和最新交接，就能继续工作，不需要重新翻阅整段聊天。

## 放行门槛

一项工作只有同时满足以下条件，才可以进入下一个切片：

- 需求边界和不做项已记录。
- 代码、测试和相关文档已同步。
- 与改动匹配的检查已经通过，失败项有解释。
- 真实验证与假服务验证被明确区分。
- 旧入口和兼容行为已经检查，过时接口没有继续被新代码引用。
- `tasks/current.md` 和交接记录已更新。

未满足时，状态写成“部分完成”或“阻塞”，不要写成“已支持”。

## 如何用这个项目学习 AI 编程

建议你每个切片都采用“人定边界，AI 做调查和实现，人做验收”的循环：

1. 你先写用户场景和验收结果，例如“选择 `gsb` 项目和 `test` 环境，运行余额接口，看到业务 `errorCode=0`”。
2. 让 AI 先只检查代码并复述方案，不立即改代码。
3. 你确认方案后，让 AI 实现一个最小切片。
4. 要求 AI 给出测试命令、实际结果、未验证项和兼容影响。
5. 你按放行门槛审查；发现问题就回到第 5 步修复。
6. 通过后更新任务和交接，再开始下一切片。

可以直接使用下面的任务提示词：

```text
请按 TestPlat 的 AI 开发 SOP 工作。
先读取 AGENTS.md、CONTEXT.md、tasks/current.md 和最新交接文件，检查三个子仓库状态。
本次只处理这个切片：<一句话目标>。
验收条件：<可观察结果>。
本轮不做：<明确延后项>。
先复述目标、入口、数据流、风险和验证计划，等我确认后再修改代码。
完成后运行匹配的检查，区分本地/假服务/真实被测系统结果，并更新 tasks/current.md 和交接记录。
```

SOP 不要求每次都新开会话。一个切片内可以连续对话；完成验收、切换领域、完成一轮审查修复或上下文接近一半到三分之二时，再按交接流程开启新会话。
