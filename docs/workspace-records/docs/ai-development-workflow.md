# TestPlat 的 AI 编程工作流

这份文档规定人和 AI 如何共同推进 TestPlat。它解决两个问题：长任务如何分段，以及新会话如何准确接手。

## 先理解文档层级

不同信息只放在一个权威位置：

| 文件 | 保存什么 | 什么时候读 |
| --- | --- | --- |
| `CONTEXT.md` | 领域术语、产品边界、长期原则 | 每次任务开始 |
| `tasks/current.md` | 当前唯一进行中的切片 | 每次任务开始 |
| `tasks/roadmap.md` | 已确认方向和建议顺序 | 规划或切换阶段 |
| `docs/ai-development-sop.md` | 一次需求从受理到放行的操作步骤和门槛 | 新增、修改、审查或排障时 |
| `docs/decisions/*.md` | 已作出的重要决定及原因 | 触及相关设计时 |
| `notes/handoff-*.md` | 阶段快照、证据、风险、接班说明 | 新会话或上下文切换时，先选最新日期 |
| 聊天记录 | 讨论过程和未确认想法 | 只作为线索，不作为事实来源 |

`CONTEXT.md` 讲“长期是什么”，`tasks/current.md` 讲“现在做什么”，决策记录讲“为什么这样做”，交接文档讲“这一阶段做到哪里”。不要把同一事实复制到多个文件；复制会让后续会话不知道改哪一份。

## 一个切片如何开始

用户提出需求后，先把它缩成一个可以在一次会话中完成的切片。切片必须有明确的结果和边界：

```markdown
# 当前任务：一句话结果

目标：完成什么可观察行为。
不做：本轮明确延后的相关事项。
涉及：Control / Engine / Assets 中的具体范围。
验收：用户可以如何操作，测试必须证明什么。
风险：依赖、兼容路径、数据或安全限制。
```

如果目标需要同时改变 UI、Control、Engine、Assets 和发布依赖，先拆开。通常先做一个最小真实闭环，再扩大范围。例如接口工作区应先完成一个真实余额接口，再接入搜索接口，最后才验证场景。

## AI 在每次会话中的固定顺序

1. 读取 `AGENTS.md`、`CONTEXT.md` 和 `tasks/current.md`。
2. 检查三个子仓库的状态、分支、最近提交和相关 diff。确认有没有未提交工作，不覆盖它。
3. 找到当前切片的入口、数据流和测试，不先凭文件名猜架构。
4. 用自己的话复述目标、非目标、验收条件和风险。若和代码或文档矛盾，先指出矛盾。
5. 先建立最小验证路径，再实现；需要设计选择时记录在决策文件。
6. 修改代码和有意义的测试。可逆、低影响的排版调整不添加无价值的镜像测试。
7. 运行与改动匹配的检查，并记录实际结果。真实业务成功、假服务成功、HTTP 成功要分别描述。
8. 更新 `tasks/current.md`：标记已完成、剩余工作、验证和下一步。
9. 若切片完成，写阶段交接，清理临时会话或调试文件，然后再开始下一个切片。

每一步都要有可检查的完成条件。比如“接口页面更好看”不是验收条件；“选择接口后显示当前环境完整 URL，编辑 `{}` 后运行成功，历史中的 request 与实际发送内容一致”才是。

## 什么时候开启新会话

在以下任一时机切换：

- 一个完整切片已经通过验证。
- 从一个领域切换到另一个领域，例如从导航 UI 切换到 Engine 依赖。
- 完成一轮审查和修复。
- 当前会话开始反复解释已经确认的事实，或上下文接近可用容量的一半到三分之二。
- 需要重新规划下一阶段，而不是继续堆叠当前实现。

不要为了每个小修复都开新会话，也不要等到上下文耗尽才切换。切换点应当是“可交接的检查点”，而不是聊天消息数量。

如果代码处于半成品状态也必须切换，`tasks/current.md` 要写清：已改文件、未完成行为、失败测试、失败是否预期、下一条具体动作。新会话先恢复这个状态，不重新设计已经决定的部分。

## 如何写交接

阶段交接使用 `notes/handoff-YYYY-MM-DD.md`。至少包括：

- 用户已经确认的产品决定。
- 已完成的行为和入口。
- 未完成、阻塞和明确不做的内容。
- 三个仓库的分支、提交和工作区状态。
- 验证命令、通过数量、真实接口证据和限制。
- 预览服务、测试数据库和不可触碰的数据。
- 下一阶段的一个推荐切片。

交接文档可以很详细，但新会话提示词要短，只指向最新交接文件和当前任务。不要把整段聊天记录复制进提示词。

## 如何记录决定

当一个选择会影响后续代码、兼容行为或用户体验时，写一个 `docs/decisions/ADR-*.md`。记录决定、背景、原因、未采用方案和影响。没有理由的代码很容易在下一会话被“简化”回旧行为。

小的实现选择留在代码和测试中，不为每个变量创建决策文件。决策文件只保存跨文件、跨仓库或跨阶段仍然有效的决定。

## 如何验证和交付

验证报告必须区分：

- 单元 / 集成测试是否通过。
- 前端 build 和 lint 是否通过。
- 假服务是否通过。
- 真实被测系统是否通过，业务断言是什么。
- 是否使用本地 editable 依赖或临时数据库。

临时调试脚本、Cookie、环境导出和含秘密的日志不进入仓库。账号、密码、主密钥和会话只保存在已有安全介质中，交接中只写“已配置”或不可逆的标识。

远程推送、合并、发布、修改真实外部系统都要单独得到授权。完成本地实现和验证后，才能把这些动作作为最后一步提出。

## 新会话启动模板

复制下面的内容即可开始新会话：

```text
请继续 TestPlat 项目。

工作区：/Users/jiavin/Developer/products/testplat1
先阅读：AGENTS.md、CONTEXT.md、tasks/current.md，以及用 `ls -t notes/handoff-*.md | head -1` 找到的最新交接文件。

先检查 testplat-control、testplat-engine、testplat-assets 三仓的 git status、分支、最近提交和相关 diff，再复述当前目标、非目标、验收条件和风险。以代码、测试和决策记录为准，不重做已经完成的功能，不覆盖未提交修改。

本次只推进 tasks/current.md 中的一个切片。先完成必要的分析和验证，再修改代码；完成后更新 tasks/current.md 和交接记录。测试使用隔离数据，不输出密码、Cookie、主密钥或未脱敏日志。不未经授权推送、合并或发布。
```

## 当前项目的学习路线

用这个项目学习 AI 编程时，按下面的循环练习，而不是只让 AI“把功能做完”：

1. 你先写目标、用户场景和验收条件。
2. AI 只做代码考察和方案复述，你检查它是否理解。
3. AI 实现一个最小切片。
4. 你要求它展示验证证据，并审查实际边界。
5. AI 修复审查问题，更新决策和交接。
6. 你决定是否进入下一个切片。

这样你学习的是需求切片、架构定位、测试设计、审查和交接，而不是学习如何一次性生成大量代码。
