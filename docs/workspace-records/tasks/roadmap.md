# TestPlat 后续路线

路线按真实用户闭环排序。每一项都要先有验收条件，再进入实现；未开始项目不应被描述为已支持。

## 当前优先：被测平台模型与配置导入

用户最新更正以 [权威需求](../docs/requirements/platforms-and-projects.md) 为准：GO2、E3E3 本身也是被测平台，各有自己的 GSB；独立后台的登录身份与处理订单的项目归属分别表达。先评估最小兼容实现，再完成 Host 与指定账号导入，具体设计尚未定稿。

本地可复现交付和接口工作区已完成相应切片；当前暂不开始 P2 搜索商品与完整场景真实验收。后续顺序由用户决定，不把旧路线当成已授权实现。

## P0：可复现和依赖收口

- 整理 Control、Engine、Assets 三仓的本地改动。
- 解决 Control 依赖的远程 Engine 版本与本地扩展不一致。
- 保留旧兼容测试，但明确正常 Web 路径只使用数据库配置。

完成条件：从干净检出或明确的本地开发方式可以复现当前已验证的请求体覆盖和登录行为。

## P1：接口管理工作区

- 按 Apifox 使用流程重排接口详情页。
- 显示接口定义、环境解析后的完整 URL、鉴权引用和请求协议。
- 保留完整请求体临时编辑与 YAML 恢复。
- 把真实响应、业务结果、耗时和执行历史放到主要视觉层级。

完成条件：余额接口可以从接口树选择、切环境、编辑请求、运行并查看真实结果。

## P2：第二个真实接口和最小场景

- 验证 `api.gsb.order.search_product` 的 Query 请求和业务断言。
- 验证 `case.gsb.smoke` 的余额 → 搜商品顺序运行。
- 记录登录缓存、参数覆盖和失败步骤。

完成条件：真实业务结果通过，不能只凭 HTTP 200 判定成功。

## P3：场景能力

- 显式步骤账号选择和账号切换。
- 跨步骤响应提取与参数传递。
- 数据驱动和场景运行结果。

开始前先确认 Engine 已有支持，避免在 Control 做一套重复执行逻辑。

## P4：测试数据与套件

- 独立测试数据模块。
- 场景套件、批量运行和筛选。
- 与执行历史、环境、账号建立明确引用关系。

## P5：Page 能力

- Page 定义的结构和元素模型。
- Page 浏览器执行适配器。
- Page 编辑、运行结果和场景引用。

Page 目前只有独立菜单和只读资产浏览，不应提前承诺执行能力。
